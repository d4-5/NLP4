# Lab 6 — classification baseline
- Task: класифікація `text_id` за домінантним типом сутності (`dominant_label` з `labels.csv`, `NO_ENTITY` якщо без сутностей).
- Features: `processed_v2` (`text_clean`), TF-IDF word n-grams (1,1) / (1,2), sublinear TF.
- Models: Logistic Regression baseline (2 варіанти для порівняння).
- Основні ризики: дисбаланс класів (`NO_ENTITY`), overlap між типами сутностей, шумна/неповна розмітка, дублікати між сплітами, трансліт/сленг.

# Lab 7 — Linear SVM + char-ngrams
- Imbalance є вираженим: у train `NO_ENTITY=4657`, а хвіст класів дуже малий (`TIME=7`, `PCT=31`, `DOC=38`, `QUANT=45`).
- Noisy text / name variation справді важливі: у помилках часто з'являються лапки, варіативні назви, змішані формати токенів і контексти з близькими сигналами.
- Char-ngrams допомогли: найкращий char-based варіант на validation дав `macro-F1=0.3906` проти `0.3432` для word-only SVM.
- `class_weight="balanced"` теж допоміг: для `word(1,2)+char_wb(3,5)` validation `macro-F1` зріс з `0.3906` до `0.4616`, а test `macro-F1` з `0.3877` до `0.4332`.
- Найпроблемніший клас за абсолютною кількістю помилок - `PERS`, бо baseline часто зводив його до `NO_ENTITY`; найнестабільніший tail-клас - `TIME`, бо у validation є лише 1 приклад.
- Для precision/recall компромісу виявилась доречною recall-first логіка для рідкісного класу `PERIOD`: custom threshold `-0.6706` підняв його recall на test з `0.1818` до `0.6364`, але зменшив recall `NO_ENTITY`.

# Lab 8 — topic modeling

- Для topic modeling використано `processed_v2` (`text_clean`); після фільтрації коротких і порожніх текстів лишилося `9930` документів із `11161`.
- Найбільші читабельні теми: держзакупівлі, суми контрактів і назви компаній, судові рішення, переліки фірм та корпоративні зв'язки.
- Корпус виглядає змішаним: поруч із новинно-бізнесовими й юридичними текстами є літературні, історичні, наукові та нормативні фрагменти.
- Шумних і шаблонних документів помітно багато: короткі фрази, службові шаблони на кшталт `Про це повідомляється...`, числовий шум і повторювані формули новин псують частину тем.
- Topic modeling тут реально корисний як інструмент дослідження структури корпусу, але найкраще працює для бізнесово-юридичних сюжетів, а не для всього змішаного набору одразу.
- Основні залишкові ризики: неоднорідність корпусу, надто загальна лексика, короткі документи, шаблонні вступи та те, що частина тем відбиває стиль подачі, а не зміст.

# Lab 9 — Word Embeddings
- **Корпус:** 11,161 текстів, очищених у `processed_v2`. Корпус достатньо великий (~800k токенів) для базових ембедінгів, але для дуже рідкісних слів контексту може бракувати.
- **Доменні терміни:** Багато термінів з держзакупівель (`тендер`, `грн`, `лот`) та юриспруденції. Ембедінги добре захоплюють їхню близькість.
- **Noisy text:** Присутній (трансліт, скорочення). FastText виглядає значно доцільнішим за Word2Vec, оскільки він враховує суб-токени (n-грами символів), що важливо для української морфології та обробки OOV/noisy слів.
- **Корисність:** Ембедінги дають корисний сигнал, особливо для групування синонімів та контекстно-близьких доменних термінів.

# Lab 10 — NER pipeline + hybrid rules
- Для цього корпусу реально важливі сутності `PERS`, `ORG`, `DATE`, `MON`, `LOC`; особливо критичні доменні `ORG` і грошові суми.
- Стандартний baseline NER pipeline корисний як стартова точка, але сам по собі недостатній: він нерівно покриває корпоративні назви, абревіатури та регулярні фінансові патерни.
- Найпроблемнішими виявилися доменні `ORG` з юридичними формами (`ТОВ`, `ПАТ`, `ДП`, `ГО`) і довгі назви установ, де часто з'являються boundary errors.
- Hybrid rules дали відчутний виграш у coverage для `DATE`/`MON` і допомогли краще витягувати частину доменних `ORG`.
- Залишкові типи помилок: boundary, type confusion (`ORG` vs `LOC`), missed domain entity, tokenization / normalization noise.

# Lab 11 — schema-first LLM extraction
- Для structured extraction протестовано кейс `document_id` + `document_type` + `date_iso` + `date_text` + `amount_value` + `amount_currency`.
- Корпус містить і явні, і неявні сигнали: суми та дати часто виражені явно, а `document_type` або релевантність `№...` іноді треба інтерпретувати з контексту.
- Складні випадки: юридичні фрагменти з кількома датами, короткі `№15`/`№610`, змішані date-only та amount-only тексти, а також приклади, де модель галюцинує документ замість `null`.
- LLM extraction виглядає життєздатним саме як pipeline, а не як одиночний prompt: на eval set `raw valid JSON rate=70%`, `post-repair valid JSON rate=100%`.
- Schema-first підхід дав стабільний structured output, але semantic exact match лишився низьким (`25%`), тож валідація структури не замінює змістовної перевірки.

# Lab 13 — multi-agent crew
- Multi-agent use case: той самий document signal extraction, але через workflow `Triager -> Extractor -> Reviewer -> Repair/Fallback`.
- Test inputs: прості юридичні тексти, missing-field кейси, ambiguous short IDs, relative dates, hallucination-prone тексти, noisy/typo фрагменти, repair і manual-review кейси.
- Очікувані типи помилок: wrong route, missed field, hallucinated document id, invalid JSON, reviewer false alarm, fallback failure.
- Fallback потрібен для коротких document IDs, noisy дат/сум, schema errors і випадків, де reviewer знаходить contradiction із source text.
- Multi-agent підхід має покращити контрольованість: reviewer ловить semantic risks, а fallback повертає partial/manual-review output замість вигаданого значення.
- Підхід надлишковий для дуже простих date-only або amount-only текстів, де rule-based extraction уже достатньо стабільний.

# Лабораторна робота 12 — Одноагентна система з інструментами (Tool-grounded)
- **Юзкейс**: Support Assistant (Оплата, Техпідтримка, Загальні питання).
- **Тест-кейси**: 10 власноруч створених сценаріїв українською мовою, що охоплюють відсутність даних, шумний текст та складні багатокрокові запити.
- **Джерело даних**: Синтетичні тікети підтримки, розроблені для перевірки правил витягу та валідації.
- **Висновки**: Витяг даних на основі інструментів є дуже надійним для структурованих полів, таких як ID замовлень та суми. Шумний текст залишається викликом для вибору інструментів LLM. Цикл ReAct забезпечує прозорість, але потребує надійного парсингу для обробки Markdown та галюцинацій.

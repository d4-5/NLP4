# Lab 10 Audit Summary

## 1. Який pipeline використано
- `Stanza` (`uk`, `tokenize,ner`)
- Рішення вибрано як готовий український baseline для NER inference без fine-tuning.

## 2. Які сутності важливі в задачі
Для цього корпусу найважливіші:
- `PERS`
- `ORG`
- `DATE`
- `MON`
- `LOC`

Особливо цінні саме доменні `ORG` і регулярні `MON`/`DATE`, бо вони часто несуть основний зміст новин про закупівлі й пов'язані сюжети.

## 3. Що baseline знаходив добре
- частину персоналій;
- короткі організації;
- частину географічних назв.

## 4. Які доменні / регулярні сутності baseline пропускав
- організації з юридичними формами (`ТОВ`, `ПАТ`, `ДП`, `ГО`);
- абревіатури на кшталт `НАЗК`, `АМКУ`, `ОДА`;
- дати у форматах `12 вересня`, `2011 року`;
- суми у форматах `9,71 млн грн.`, `5 тис грн.`, `$25 тис`.

## 5. Які rules були додані
- regex для `MON`;
- regex для `DATE`;
- rule-based `ORG` extraction через legal forms і acronym dictionary;
- post-processing для корекції меж `ORG`.

## 6. Що вони реально покращили
- підвищили coverage для регулярних сутностей `MON` і `DATE`;
- додали частину пропущених доменних `ORG`;
- зменшили кількість явних boundary помилок у назвах компаній.

## 7. Які категорії помилок були наймасовішими
Очікувано найчастіше трапляються:
- `boundary error`;
- `missed domain entity`;
- `false positive`;
- `type error` (`ORG` vs `LOC`);
- `tokenization / normalization issue`.

## 8. Що б я робив далі
- розширив словники організацій і державних установ;
- додав окремі правила для nested spans;
- порівняв `Stanza` зі `spaCy` як другим baseline;
- за наявності часу зробив би більш формальний per-type evaluation report.
